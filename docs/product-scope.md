# 产品范围与 MVP

本文用问答形式说明这个产品是什么、给谁用、当前能做什么、明确不做什么。
问题是按"使用者会问的顺序"排的，不是按模块排的。

---

## 这是什么？

**Q：一句话说明这个产品做什么？**

WebMonitoring 持续检测**已授权**的网页是否发生了异常变化，并在变化发生时
给出可核查的证据、差异和处置记录。它回答的是监测与取证问题。

**Q：它不做什么？**

它**不是** WAF、主机入侵检测、漏洞扫描器或自动修复工具。它不拦截请求、不改
客户网站、不做漏洞利用或密码破解。

**Q：和"我每天手动看一遍网页"比，价值在哪？**

手动看只能看到当下，看不到"和昨天比变了什么"，也留不下可比对的证据。
这个产品保存基线版本、逐轮差异信号和原始快照，让"变了吗、变了什么、
是不是恶意的、谁在处理"四个问题都有据可查。

---

## 它回答哪些问题？

1. 哪个**已授权页面**发生了异常？
2. 异常具体**改变了什么**？
3. 变化是否具有**恶意特征**？
4. **证据在哪里**，谁负责处理，是否已经恢复？

## 目标用户

| 用户 | 主要目标 |
| --- | --- |
| 安全运营人员 | 发现、研判、分派和关闭安全事件 |
| 网站运维人员 | 获取差异证据、定位发布或篡改来源 |
| 业务负责人 | 关注重点页面可用性、品牌和业务风险 |
| 审计人员 | 查询告警、证据、操作记录和处置时效 |
| 平台管理员 | 管理租户、资产、角色、节点和通知渠道 |

## 怎么用？（核心流程）

**Q：从零到看到第一个事件，要走哪几步？**

```text
按租户（slug）登录
-> 登记站点
-> 登记资产（可选归属站点）
-> 完成授权验证
-> 配置策略
-> 创建或批准基线
-> 定时检测
-> 提取信号
-> 生成风险结论
-> 保存证据
-> 发送告警
-> 事件处置
-> 恢复确认
-> 复盘和报告
```

**Q：为什么必须先"授权验证"？**

这是不可妥协的产品前提：只检测已登记且完成所有权验证的目标。三种验证方式是
HTTP 文件令牌（FILE）、DNS TXT（DNS）和 HTML meta 标签（META）。没通过验证
的资产不会被调度检测——这是失败关闭，不是可以跳过的步骤。

**Q：登录是按什么区分租户的？**

按租户 slug 进入对应租户，slug 为空则回落默认租户。平台管理员（SUPER_ADMIN）
可创建租户，并在创建时播种该租户的首个管理员账号。

## 当前能做什么？

下面按"你能提出的需求"来组织。每项都对应代码和测试，可直接使用。

### 资产中心

**Q：能登记什么样的资产？**

租户内页面资产，含负责人、页面类型和站点归属。页面类型有官网、业务前台、
后台登录页和其他重点页面。

**Q：所有权怎么证明？**

三种方式任选：HTTP 文件令牌（FILE）、DNS TXT（DNS）和 HTML meta 标签（META）。

**Q：资产多了怎么批量管理？**

支持批量导入/导出（JSON/CSV，逐行校验，允许部分失败）。资产的启停、暂停/恢复
和变更审计都已具备。

### 租户与站点管理

**Q：站点和租户分别谁能改？**

站点（Site）CRUD：租户内 ADMIN 可创建/编辑/**删除**，资产可归属站点并按站点
过滤。删除站点时若其下仍有资产会被拒绝（`409 SITE_NOT_EMPTY`），需先解除归属——
不会静默把资产挪成「无所属」。
租户（Tenant）CRUD：平台管理员（SUPER_ADMIN）可创建/编辑，创建时同时播种该租户
首个 ADMIN 账号；登录可按租户 slug 进入对应租户。

**Q：SUPER_ADMIN 能看到所有租户的数据吗？**（"我不能干什么"的一例）

**不能。** super-admin 权限仅限租户 CRUD 与播种租户管理员，不做任意租户数据的
全量可见，也不做租户硬删除。

### 检测中心

**Q：检测拿到的信息有哪些？**

- HTTP 状态、响应时间、大小、响应头、TLS 和 DNS。
- 重定向链、最终域名和最终地址复核。
- HTML 原文摘要和规范化 DOM 摘要。
- 标题、正文、关键区域、脚本、iframe、链接和表单变化。
- 浏览器渲染后的截图、跳转、弹窗和下载行为。
- 超时、响应过大、检测节点失败等检测异常。

**Q：HTTP 和浏览器两种检测有什么区别？**

HTTP 检测抓原始响应，快、轻量；浏览器检测用真实 Chromium 渲染后再分析，能看
到 JS 执行后的 DOM、截图、弹窗和跳转。见
[architecture.md](architecture.md) 的检测 Worker 一节。

**Q：需要登录才能看的页面能检测吗？**

可以。客户凭据用 AES-256-GCM 加密存储，登录地址在控制面和 Worker 两侧各做一次
SSRF 复核，登录后抓取受保护页面，API 响应不泄露凭据。浏览器模式下凭据由控制面
解密后经内部 HTTP 传给 Worker。

### 基线和规则

**Q：第一次检测会直接报警吗？**

不会。首次检测只产生**候选基线**，不自动覆盖已批准基线。没有已批准基线时不会
产生差异事件（这也让压测的"0 假阳性"断言可测）。

**Q：基线能回退吗？**

基线版本可查看、批准、废弃，原版本保留。

**Q：正常会变的区域（时间戳、轮播图）会不会天天报警？**

可以配置动态区域、可信资源、维护窗口和误报抑制。规则版本和风险评分记录在每次
检测结果中。

### 事件中心

**Q：事件怎么产生和去重？**

相同异常聚合去重；风险级别分提示、低、中、高、严重。

同一指纹（同资产、同基线版本、同异常）**只会有一行事件**，无论中间被关掉过几次。
已经**关闭或标为误报**的问题再次出现，会**重开原来那一行**并追加一条「问题回归」
（`REOPENED`）时间线，而不是插出一条新的重复事件——运营因此能看出是同一个问题
回来了。注意：**已恢复（RESOLVED）不属于重开范围**，它复现后状态不变，只有出现
次数继续增长；重开也不抹掉上一轮的处置时间。

**Q：处置动作有哪些？**

认领、指派、备注、误报、处理中、已恢复、已关闭。每个事件都有证据清单和操作审计。

**Q：能看到一个事件从头到尾发生了什么吗？**

能。事件时间线（`incident_events`，append-only）记录每轮复现各自的信号集、
状态流转、负责人变更和备注。注意：事件行上的 `signals` 每轮被覆盖，
复现明细只存在于时间线里。时间线条目不参与保留期清理。

**Q：告警能发到哪里？**

Webhook、企业微信、钉钉和邮件。投递有记录、重试和事件级去重。

### 报告中心

单事件证据包；按时间范围、资产范围和风险范围的报告；以及检测覆盖率、告警数量、
平均发现时间（MTTD）和平均恢复时间（MTTR）。

## 当前明确不做

这一节说的是**产品边界**，不是"以后会做"的路线图。凡在下列范围内的，
本产品不提供，也不应被期待。

**Q：会做开放式扫描吗？**

不会。只检测已登记的资产，不做未经资产登记的开放式扫描。

**Q：会做漏洞利用、密码破解、绕过认证或攻击验证吗？**

不会。本产品是监测与取证工具，不做任何主动攻击性动作。

**Q：会自动帮我修复被篡改的页面吗？**

不会。产品不做自动修改客户网站或基础设施——恢复动作由人在受控流程中进行。

**Q：会用大模型替代规则判断吗？**

不会。模型不得替代规则、哈希、DOM、网络和浏览器信号。模型输出是数据，
不改变权限或任务边界。

**Q：会提供不经审计的批量删除吗？**

不会。不具备审计和回滚能力的批量删除不在范围内。

**Q：会不会上微服务、分布式爬虫、大数据平台？**

不会在没有容量依据时引入。当前是**单机 Docker Compose**部署，这是有意选择：
在没有实测规模依据前，不预先引入 Kubernetes 或分布式架构。

**Q：会不会做资源级的细粒度权限和双人审批？**

**当前不提供。** 角色只有 ADMIN / OPERATOR / AUDITOR / SUPER_ADMIN 四种，
按端点做粗粒度校验，**没有** `asset:read` 这类资源级权限集，也**没有**高风险
操作的双人审批。前端权限只到角色级。这意味着：**同一租户内的 ADMIN 能读写
该租户的全部资源**。如果你的场景要求"某个管理员只能管某几个资产"，本产品
现在做不到。

**Q：会不会做计费、配额、租户自注册、跨租户管理员？**

**当前不提供。** 没有租户配额或计费，租户只能由 SUPER_ADMIN 创建（不能自注册），
也没有跨租户切换的管理员视图。

**Q：密钥会托管到外部 KMS/Vault 吗？**

**当前不提供。** 主密钥以明文环境变量注入（`ALERT_SECRET_KEY` /
`ALERT_SECRET_KEYS`）。版本化轮换和存量密文再加密扫描都已具备，
但**尚未在真实数据上执行过**，也未接入外部密钥托管——进程环境里目前会出现明文密钥。

**Q：支持 AWS S3 这类外部对象存储吗？**

代码支持 S3 兼容接口，MinIO 上已实测跑通，但**外部 S3 实机演练尚未执行**
（见 [object-storage-rehearsal.md](object-storage-rehearsal.md)，状态为「尚未执行」）。
区域解析与预签名 URL 这两条路径在 AWS S3 上可能不同，未验证前不应假定可用。

**Q：能部署到 Kubernetes 吗？**

当前只有单机 Compose，无 Kubernetes 与 Helm 清单。

## 怎么判断它做对了？

**Q：MVP 的验收标准是什么？**

- 可在租户内登记一个已授权 URL，并完成基线审批。
- 正常动态内容可以通过配置被忽略。
- 新增外部脚本、恶意跳转和明显内容替换可产生可解释事件。
- 每个事件都能查看原始证据、差异和规则版本。
- 重复检测不会重复创建相同事件或告警。
- 事件状态、负责人和处置记录可审计。
- 检测目标、证据和通知失败时均有明确错误状态。

**Q：有准确率承诺吗？**

没有绝对准确率承诺。初始阶段先建立可测量基线：授权资产检测成功率、证据完整率、
高风险事件的证据关联率、重复事件率、误报率及误报关闭原因分布、平均发现时间
（MTTD）、平均确认时间（MTTA）、平均恢复时间（MTTR）。

**Q：结论可以直接当"被入侵"的证据吗？**

不能。所有高风险告警都是**辅助研判**，不是自动定罪。产品文案使用"检测到疑似"
"命中以下信号""建议核查"等可验证表达，避免无证据的绝对结论。
