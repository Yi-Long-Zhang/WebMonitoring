# 安全模型与威胁边界

本文用问答形式说明信任边界、主要威胁和当前的权限模型。**读者**：安全评审人、
决策者，以及需要判断"这个系统会不会成为新风险点"的人。

---

## 信任边界在哪里？

**Q：谁信任谁？**

```text
客户管理员
  -> 控制面 API
      -> 任务队列
          -> HTTP Worker / Browser Worker
              -> 外部或客户授权目标
      -> PostgreSQL / Object Storage
```

**Q：监测目标算可信服务吗？**

**不算，它是潜在恶意输入。** Worker、控制面、数据库和对象存储之间都必须有明确的
身份认证和最小权限。

**Q：整个系统的安全前提是什么？**

只对**已登记且完成所有权验证**的目标做检测。这是失败关闭的：授权校验失败必须
拒绝执行，不是"记录一下继续跑"。

## 主要威胁

### SSRF 和网络逃逸

**Q：防哪些地址？**

内网地址、回环地址、链路本地地址、云元数据地址，以及 DNS Rebinding、重定向绕过、
非 HTTP 协议、任意端口和超大响应。

**Q：具体怎么防？**

- 只允许明确协议和端口。
- URL 解析、域名解析和实际连接之间**复核地址**（防止 DNS Rebinding）。
  这一点在两条检测路径上的**强度不同**：HTTP Worker 用 `DialContext` 把连接钉在已校验的
  IP 上（`internal/security/urlguard.go`），解析与连接之间没有窗口；浏览器 Worker 是
  「先解析校验、再让 Chromium 自己解析」，两者之间仍留有一个 TOCTOU 窗口。
  `状态：部分实现 —— 浏览器路径的 DNS Rebinding 防护只覆盖地址判定，未把连接钉到已校验 IP。`
- **每次重定向重新执行授权与网络安全校验**。
- 阻断 loopback、link-local、private、reserved 和 metadata 地址。**地址判定在两条路径上
  对齐**：IPv4 与 IPv6 都按同样的语义判，包括把 IPv4-mapped（`::ffff:127.0.0.1`）折叠成
  它承载的 IPv4 再判——此前浏览器侧只做字符串前缀匹配，这一类地址是被放行的
  （`apps/browser-worker/src/security.ts`）。
- 限制重定向次数、连接时间、总时间、响应大小和并发数。
- 私网检测只能在客户控制的检测节点和明确网络策略下启用（`ALLOW_PRIVATE_TARGETS`，
  默认 `false`）。

**Q：登录态检测的登录地址也走这套校验吗？**

走，而且是**两侧各一次**：控制面和 Worker 都做 SSRF 复核。登录页一旦被拦截即
失败关闭，避免把渲染失败的登录页当成受保护页面存成快照。

### 恶意网页和浏览器逃逸

**Q：网页里的 JS 能逃出浏览器吗？**

我们的责任是把它关住：

- 浏览器运行在隔离容器或沙箱中。
- 禁止访问 Worker 凭据、主机文件、控制面内部接口和云元数据。
- 限制浏览器上下文的存储、下载、弹窗、脚本和网络权限。
- **不把网页内容拼接进系统提示词或高权限工具指令**——网页 HTML、脚本、截图、
  响应文本和模型输出都是**数据**，不得改变权限或任务边界。

### 凭据和敏感数据

**Q：客户的登录凭据怎么存？**

登录态检测必须有明确授权。凭据用 AES-256-GCM 加密，密文的关联数据绑定
`<tenantID>:<assetID>:auth`，因此密文不能跨行搬移。API 响应不泄露凭据。
**已知边界**：主密钥当前以明文环境变量注入，未接入外部 Secret Manager/KMS。

**Q：日志里会出现敏感数据吗？**

不会。日志、Trace、错误、截图和模型输入**不得**包含密码、Token、Cookie、授权头、
身份证件、个人联系方式和敏感表单值。

**Q：改了密码以后，别人手上那个 Cookie 怎么办？**

**立刻失效。** 会话记录里存着签发时的密码指纹（`sha256` 后的密码校验值），每次请求都会
拿它和仓储里当前的密码比对：不一致就删掉会话并回 401。密码哈希本身带随机盐，所以任何一次
重设——包括把密码设成和原来一样——都会产生新的指纹。

**只有执行改密的那个会话会被保留**，其余全部失效。保留它是有意的：改密码最常见的原因正是
Cookie 被盗，如果改完把自己也踢出去，等于在训练用户回避唯一能吊销泄露凭据的动作。
停用用户与停用租户同样会让会话在下一次请求即失效。

在此之前，"改密码"只改了密码——已经拿到的会话会一直有效到 12 小时的 TTL 到期。

**Q：证据怎么下载？**

通过已认证 API 完成租户校验，并在返回前校验对象大小和 SHA-256。

**Q：短时签名下载链接是怎么签的？**

两条路径，取决于证据存在哪里（默认 5 分钟过期，
`EVIDENCE_SIGNED_URL_TTL_SECONDS` 可调）：

- **本地证据**：由控制面签发 HMAC-SHA256 链接，带域分离标签
  与定长时间比较；请求仍需过 `ReadVerified`，因此仍会校验对象完整性。
- **S3/MinIO 证据**：不过控制面，改为对象存储自己的
  **预签名 GET**（`PresignedGetURL`），签名和完整性由存储保证。

### 多租户越权

**Q：怎么防止 A 租户读到 B 租户的数据？**

- 所有租户资源查询都**必须**带租户边界。
- 从 URL、请求头或前端参数中取得的 `tenant_id` **不得直接信任**。
- 站点与资产、负责人的租户一致性由复合外键 `(tenant_id, site_id)`、
  `(tenant_id, owner_id)` 在**数据库层**强制，应用层同时用 `GetSite`/`GetUser`
  校验并失败关闭。
- 证据对象的访问鉴权必须与业务资源一致。

**Q：跨租户管理员能看到所有租户数据吗？**

**不能。** 当前 `SUPER_ADMIN` 仅限租户 CRUD 与播种租户管理员，**不做**任意租户
资产/事件的跨租户可见；租户/站点 CRUD 全部记审计。

### 证据篡改和不可抵赖

**Q：证据写入后能被改吗？**

不能。原始证据写入后不可更新；保存内容计算摘要并校验对象大小和媒体类型；
派生分析引用原始证据 ID、规则版本和分析时间；删除和保留期变更必须有授权和审计。

**Q：这是不可妥协的吗？**

是。**证据先于结论**——没有证据引用，不得声称页面已被篡改；**原始证据不可覆盖**
——只能追加衍生分析，不能覆盖已保存的原始快照。

## 权限模型

**Q：现在有哪些角色？**

四种：`SUPER_ADMIN`（平台级租户 CRUD 超集）、`ADMIN`（租户内管理）、
`OPERATOR`（安全运营）、`AUDITOR`（只读审计）。`SUPER_ADMIN` 在其自身租户内
视同管理员。

**Q：有资源级细粒度权限吗？**

**没有。** 按端点做粗粒度校验，**没有** `asset:read` 这类资源级权限集，
**没有**字段级授权。直接后果：**同一租户内的 ADMIN 能读写该租户的全部资源**，
无法限定"某管理员只能管某几个资产"。也没有高风险操作的二次确认或双人审批。

**Q：那"菜单隐藏"算权限控制吗？**

**不算。** UI 隐藏不能代替后端权限校验。菜单隐藏不是权限控制，后端必须鉴权。

**Q：如果一个系统将来需要细粒度 RBAC，粒度该到哪一级？**

（这是**目标形态的描述**，不是当前实现。）权限粒度至少应覆盖：

```text
asset:read / asset:write / asset:delete
monitor:run / monitor:write
baseline:approve / baseline:retire
incident:read / incident:assign / incident:close
evidence:read / evidence:export / evidence:delete
integration:read / integration:write
admin:tenant / admin:user / audit:read
```

高风险权限应支持二次确认或双人审批。

## 数据分类和留存

| 类别 | 示例 | 默认策略 |
| --- | --- | --- |
| 公开页面数据 | 页面标题、公开正文 | 按租户策略留存 |
| 安全证据 | HTML、截图、资源清单 | 不可覆盖，按策略留存 |
| 配置数据 | 资产、规则、基线元数据 | 版本化和审计 |
| 敏感凭据 | 密码、Cookie、Token | 不进普通库、日志和模型 |
| 审计数据 | 登录、变更、处置操作 | 不可静默修改 |

**Q：证据默认留多久？**

证据 **90 天**、审计 **365 天**。实际留存期限由合同、法规和租户策略确定。
代码**不得**假设所有证据永久保存。

**Q：什么东西不能被静默清掉？**

审计数据不可静默修改；事件时间线（`incident_events`，append-only）不参与保留期
清理；被事件或基线引用的证据永不删除。

## 告警和外部通知

- 证据写入成功后才发送正式告警。
- 通知内容只包含最小必要信息，不直接嵌入敏感原文。
- 渠道失败应重试并记录最终失败，**不阻塞事件落库**。
- Webhook 必须签名、限速和防重放。

**Q：Webhook 签名覆盖什么？**

覆盖 UTC Unix 时间戳和请求体。**接收方仍需自行实现时间窗口校验和去重**——
签名不替你防重放。

**Q：告警会无限重试吗？**

不会。出站告警有每渠道滑动窗口配额（`ALERT_MAX_PER_CHANNEL_PER_WINDOW`）与连续
失败熔断（`ALERT_FAILURE_THRESHOLD` + `ALERT_CIRCUIT_COOLDOWN_SECONDS`）。
两者都是**失败开放**（fail open）的：控制在正常工作时有效，出问题时不阻塞事件落库。
通知去重键必须与事件去重策略一致。

## 安全测试要求

**Q：必须覆盖哪些测试？**

- SSRF 地址、DNS 变化、重定向和端口边界。
- 租户越权读取和写入。
- 恶意 HTML、脚本、URL 和文件名。
- 证据下载过期、越权和内容类型伪造。
- 队列重复消费、超时、死信和告警重试。
- 日志脱敏和错误响应。

## 平台自身出安全事件了怎么办？

**Q：处置步骤是什么？**

1. 停止扩大影响的任务和通知。
2. 保留相关审计、任务和证据。
3. 标记受影响租户、资产和时间范围。
4. 由人工确认是否暂停相关 Worker 或凭据。
5. 记录修复、验证和复盘结果。

**Q：什么时候必须停下来上报而不是自行处理？**

证据的 SHA-256 校验不一致（可能是证据被篡改或损坏）、需要从备份恢复 evidence
bucket、需要删除任何证据元数据行或对象、需要更换 `S3_*` 凭据或迁移存储——
这些都**先停手、保留现场**，走授权与审计。

## 安全边界声明

本系统用于**经授权的完整性监测和防御性分析**。任何绕过认证、漏洞利用、
密码破解、隐蔽扫描和未授权目标探测都**不属于产品能力**。
