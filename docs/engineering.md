# 工程协作与开发提交规范

## 1. 当前开发阶段

功能闭环已完成，当前是投产前验证与按场景投产阶段（见
[adr/0005-post-mvp-stage.md](adr/0005-post-mvp-stage.md)），优先级如下：

```text
可运行
> 数据与状态模型稳定
> 检测和证据可信
> 安全边界完整
> 测试可重复
> 功能数量
> 性能优化
```

不为了“看起来像完整产品”提前引入微服务、复杂权限平台、自动恢复或完整多租户运营后台。未完成的生产能力必须在文档中标记为部分实现或规划中；标注统一用在功能描述处就地书写的 `状态：部分实现 —— <缺口>` 或 `状态：规划中 —— <缺口>` 字段，未标注的能力默认视为已实现（词表见 [README.md](README.md) 状态用语一节）。

## 2. 分支规则

推荐使用：

```text
main                 # 当前可运行、可演示的集成基线
feature/<topic>      # 新功能
fix/<topic>          # 普通缺陷
security/<topic>     # 安全修复
docs/<topic>         # 文档和决策记录
codex/<topic>        # Codex 环境默认工作分支
```

当前单人或小团队阶段不强制引入 `develop`。功能分支完成适用门禁后合并到
`main`；在生产验收项完成前，合并到 `main` 不代表可发布。
分支名使用小写英文和短横线，避免把需求全文放进分支名。

## 3. 分支开发与合并

### 基本概念

- **分支（branch）**：从某个提交点分出的独立开发线，用于隔离一个功能、
  缺陷、安全修复或文档目标。
- **提交（commit）**：对一组相关文件变更形成的不可变版本记录。一个提交
  应表达一个清晰目的，并能够单独解释和验证。
- **合并（merge）**：把一个分支的提交整合到另一个分支，通常是把已完成的
  功能分支合入 `main`。
- **合并提交（merge commit）**：同时拥有两个或更多父提交的特殊提交，用来
  记录两个开发历史已经完成整合。它不是新的业务功能提交，不应替代功能分支
  中必要的功能提交。
- **变基（rebase）**：将当前分支的提交重新应用到新的基线之上，会改变提交
  的 ID。只对尚未共享的个人分支使用，已推送或他人正在使用的分支不得随意
  变基。
- **快进合并（fast-forward）**：目标分支没有独立新提交时直接移动分支指针，
  不产生合并提交。它适合简单、线性的变更，但不会保留分支边界。

### 推荐流程

```text
从 main 更新本地基线
-> 创建一个目标明确的开发分支
-> 在开发分支上进行小步提交
-> 运行适用的格式化、构建、测试和安全检查
-> 检查 diff、staged 文件和提交历史
-> 将开发分支合并到 main
-> 在 main 上再次确认状态和验证结果
```

建议遵循以下规则：

- 一个开发分支只处理一个清晰目标；发现无关改动时应拆分到其他分支。
- 开发分支应从最新的 `main` 创建。合并前如存在明显基线偏差，应先在开发
  分支上同步并重新运行受影响的检查。
- `main` 只接受已经完成适用门禁的分支。合并到 `main` 表示进入集成基线，
  不表示已经完成生产发布验收。
- 有代码评审、审计或回滚需要时，优先使用保留分支边界的合并提交，例如：

  ```powershell
  git switch main
  git merge --no-ff feature/<topic>
  ```

- 分支上的提交已经清晰、数量合理时，保留原提交历史；如果分支包含大量
  `WIP`、试错或修正提交，且不需要保留这些过程，可在合并前整理或采用
  squash 合并，但不得丢失最终变更说明和验证记录。
- 合并冲突必须人工理解和解决。不能用整文件覆盖、强制回退或跳过测试来消除
  冲突；解决后必须重新运行受影响的检查。
- 不直接在 `main` 上开发高风险或跨模块功能，不使用 `git add .` 把未审查
  的文件带入合并。
- 合并完成后，已合并分支可以删除；`main`、发布标签和审计所需的提交记录
  不得删除或重写。

### 合并提交与发布的区别

合并提交只说明代码历史已经整合，不能证明：

- Docker Compose 已经实测。
- 数据库迁移和回滚已经演练。
- Redis pending 消息恢复已经验证。
- 生产网络、密钥、监控和容量要求已经满足。

这些内容必须通过发布门禁和验收记录单独确认。

## 4. 提交规则

### 提交粒度

一个提交只完成一个清晰目的，例如：

```text
添加资产领域模型
实现 URL 网络安全校验
增加基线差异测试
补充事件状态机文档
```

以下内容不要混在功能提交中：

- 无关格式化。
- 全项目依赖升级。
- IDE 私有配置。
- 与当前任务无关的重命名。
- 未解释的生成文件和构建产物。

OpenAPI 变更必须同步检查生成的前端类型；数据库行为或安全边界变更必须同步
检查迁移、回滚说明、相关测试和受影响文档。生成文件可以进入同一提交，但必须
说明来源文件和生成命令。

### Commit Message

使用 Conventional Commits：

```text
<type>: <summary>
```

推荐类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `security` | 安全修复或安全策略变更 |
| `test` | 测试 |
| `refactor` | 不改变外部行为的重构 |
| `docs` | 文档 |
| `chore` | 工具、依赖和构建 |

示例：

```text
feat: add asset authorization workflow
fix: block private address redirects
security: isolate browser worker network access
test: cover baseline diff normalization
docs: define incident state transitions
```

标题使用动词开头，尽量不超过 72 个字符，不在标题末尾加句号。
安全修复需要在提交正文或 PR 描述中说明影响、修复和验证方式。

## 5. 提交前门禁

提交前至少执行适用项目检查：

```text
格式化
-> 编译或类型检查
-> 相关单元测试
-> 集成或 E2E 测试
-> 安全和敏感信息检查
-> staged 文件检查
```

当前仓库是 Go 模块和 pnpm workspace。Go 代码至少执行：

```text
go test ./...
go vet ./...
gofmt -w <changed-go-files>
```

其中 `internal/api` 里跑着一条**契约 ↔ 路由一致性门禁**
（`internal/api/routes_contract_test.go`）：它比对 `server.go` 的 `routes()` 与
`api/openapi.yaml` 的 operation 集合，少了任何一边都会红。**加了 handler 就要写契约
并重新生成 client 类型**（`corepack pnpm --filter @webmonitoring/console generate:api`），
否则两道门禁会分别拦住你（这一条拦路由，CI 的 `git diff --exit-code api.d.ts` 拦类型）。

当前前端 workspace 支持：

```text
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build
```

若本地环境不支持 `pnpm` 入口，使用等价的 `corepack pnpm` 命令。适用门禁失败
时不得把变更描述为已完成；如确需保留功能分支上的中间提交，必须在提交说明、
PR 或最终报告中明确失败原因和未完成项，且不得合并到 `main` 作为可用功能。

### 控制台的几条前端约定

这些是踩过之后定下来的，改控制台时按它们做，理由见 `docs/rehearsals.md`
的阶段二 2.3：

- **首次加载用 `firstLoad`，不要用 `loading`** 驱动骨架屏。`loading` 在每次刷新
  （含事件流触发的那次）都为真，用它会让有数据的表格每几秒退回骨架。
- **空态**：表格用 Element Plus 的 `empty-text`；其余用
  `components/system/EmptyState.vue`，不要直接写 `el-empty`（尺寸会各处漂移）。
- **错误边界在 `App.vue`**：`render`/`setup` 失败才用兜底页替换视图；watcher、
  异步处理器与生命周期钩子的失败只出顶栏横幅——把操作员眼前正常的页面换成错误页
  是更糟的结果。
- **组件测试跑在 jsdom 里**（`vite.config.ts` 的 `test` 块）。Element Plus 的表格
  表体在 jsdom 里渲染不出来（测量全为 0），用 `src/test/elTableStub.ts` 的桩，
  表格自身渲染由 `compose-smoke.ps1` 在真实浏览器覆盖。
- **接口给的值要按契约防御性读取**：服务端出现过「契约写 required array、实际返回
  `null`」（策略的 `ignoreSelectors`/`trustedDomains`），前端直接 `.join()` 会崩。


## 6. Agent 提交权限

- 默认：Agent 可以读、改、测试和准备 staged 内容，但不自动 `git commit`。
- 用户明确要求“提交”或“创建 commit”后，Agent 才可以执行 commit。
- 默认不执行 `git push`，除非用户明确要求。
- commit 前必须展示或报告待提交文件和 commit message。
- 不得通过 `git add .` 把无关文件、密钥、客户数据和构建产物带入提交。
- 不得重置、覆盖或清理用户已有改动。

### 自动提交与自动合并

自动提交和自动合并属于**显式授权的可选流程**，不是默认行为。授权必须来自
当前任务的明确指令，不能仅根据历史习惯、配置文件或“检查已通过”推断。

允许自动提交前，必须同时满足：

- 已明确指定目标分支；未指定时只允许提交当前开发分支，不得猜测目标。
- 已检查工作区，确认没有未授权的用户改动、敏感文件、客户数据或构建产物。
- 已按变更范围执行格式化、编译/类型检查、测试、安全检查和 staged 文件检查。
- commit message 符合 Conventional Commits，并且提交目标与分支目标一致。
- 已向用户报告待提交文件、commit message、测试结果和迁移/回滚影响。

允许自动合并前，除上述条件外还必须满足：

- 合并目标只能是用户明确指定的分支；默认目标为 `main` 时，必须明确说明
  “合并到 main”。
- 开发分支相对目标分支无未解决冲突，且合并后再次运行适用门禁。
- 合并不会跳过代码评审、必需的 CI 检查、数据库迁移检查或安全复核。
- 高风险变更、生产配置、凭据、恢复、删除、外部系统修改和基础设施变更
  不得自动合并，必须人工确认。
- 自动合并到 `main` 只代表进入集成基线，不代表完成生产发布。

合并策略按以下顺序选择：

1. 提交历史清晰且需要保留分支边界时，使用 `merge --no-ff`。
2. 分支包含多个仅用于试错的 `WIP` 提交时，可在合并前整理或 squash，但必须
   保留完整的最终变更说明和验证记录。
3. 存在冲突、门禁失败、范围不明或用户改动无法区分时，停止自动化流程并请求
   人工处理。

自动提交/合并流程不得自动执行 `git push`、删除远程分支、创建发布标签或发布
生产版本；这些动作需要单独授权。任何一步失败都必须保留失败现场并报告原因，
不得伪装成提交或合并成功。

## 7. 评审规则

评审优先看：

1. 数据越权、SSRF、凭据泄露和证据篡改。
2. 状态机非法流转、重复事件、丢失告警和错误重试。
3. 检测误报、漏报和不可解释结论。
4. API 契约、迁移兼容性和租户边界。
5. 测试缺口和不可观测的失败路径。

PR 或合并说明至少包含：

```text
目标
改动
风险
测试与结果
数据库/配置/迁移影响
回滚方式
```

## 8. 发布规则

开发提交、合并和发布是三个不同动作：

```text
commit -> review/merge -> release
```

发布必须具备：

- 明确版本或构建标识。
- 数据库迁移顺序和回滚策略。
- 配置和密钥变更清单。
- 关键健康检查。
- 监控和告警确认。
- 失败后的停止和回滚方案。

当前仓库把 Docker Compose smoke、真实 PostgreSQL/Redis 集成、Redis pending
恢复、备份恢复演练和监控检查作为正式交付门禁。代码门禁已由 CI 配置覆盖；
在具备 Docker 和基础设施的验收主机执行并留存结果前，`main` 仍只能视为
候选交付基线。未经验证的自动恢复、生产网站修改和基础设施变更不得作为普通
发布步骤。

## 9. 变更分类

| 分类 | 示例 | 最低要求 |
| --- | --- | --- |
| 文档 | 说明和 ADR | 文档检查 |
| 低风险代码 | 展示、普通查询 | 格式化、编译、相关测试 |
| 领域变更 | 状态机、评分、基线 | 单测、迁移检查、事件回归 |
| 安全变更 | SSRF、权限、凭据、隔离 | 负向测试、审计、人工复核 |
| 高风险操作 | 恢复、删除、外部配置 | 明确授权、演练、回滚验证 |

## 10. 生成物和环境

- `.env`、密钥、证书、客户数据和真实证据不得提交。
- `.idea/` 等个人 IDE 配置默认不属于产品提交。
- 测试夹具应使用合成数据和脱敏页面。
- 生成代码必须注明来源和生成命令，源文件变更后重新生成。
- 本地对象存储、PostgreSQL 和 Redis 数据目录不得进入 Git。
