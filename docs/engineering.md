# 工程协作与开发提交规范

## 1. 当前开发阶段

当前是 MVP 设计和基础能力建设阶段，优先级如下：

```text
可运行
> 数据与状态模型稳定
> 检测和证据可信
> 安全边界完整
> 测试可重复
> 功能数量
> 性能优化
```

不为了“看起来像完整产品”提前引入微服务、复杂权限平台或自动恢复。

## 2. 分支规则

推荐使用：

```text
main                 # 可运行、可演示、可发布基线
feature/<topic>      # 新功能
fix/<topic>          # 普通缺陷
security/<topic>     # 安全修复
docs/<topic>         # 文档和决策记录
```

当前单人或小团队阶段不强制引入 `develop`。功能分支完成验证后合并到 `main`。
分支名使用小写英文和短横线，避免把需求全文放进分支名。

## 3. 提交规则

### 提交粒度

一个提交只完成一个清晰目的，例如：

```text
添加资产领域模型
实现 URL 网络安全校验
增加基线差异测试
补充事件状态机文档
```

以下内容不要混在功能提交中：

- 无关格式化。
- 全项目依赖升级。
- IDE 私有配置。
- 与当前任务无关的重命名。
- 未解释的生成文件和构建产物。

### Commit Message

使用 Conventional Commits：

```text
<type>: <summary>
```

推荐类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `security` | 安全修复或安全策略变更 |
| `test` | 测试 |
| `refactor` | 不改变外部行为的重构 |
| `docs` | 文档 |
| `chore` | 工具、依赖和构建 |

示例：

```text
feat: add asset authorization workflow
fix: block private address redirects
security: isolate browser worker network access
test: cover baseline diff normalization
docs: define incident state transitions
```

标题使用动词开头，尽量不超过 72 个字符，不在标题末尾加句号。
安全修复需要在提交正文或 PR 描述中说明影响、修复和验证方式。

## 4. 提交前门禁

提交前至少执行适用项目检查：

```text
格式化
-> 编译或类型检查
-> 相关单元测试
-> 集成或 E2E 测试
-> 安全和敏感信息检查
-> staged 文件检查
```

当前仓库只有 Go 模块声明，命令以实际工程文件为准。后续 Go 服务至少应支持：

```text
go test ./...
go vet ./...
gofmt -w <changed-go-files>
```

前端建立后至少应支持：

```text
npm run typecheck
npm run lint
npm run test
npm run build
```

命令失败时可以提交到功能分支的脚手架提交，但必须在提交说明、PR 或最终报告中
明确失败原因和未完成项，不得合并到 `main` 作为可用功能。

## 5. Agent 提交权限

- 默认：Agent 可以读、改、测试和准备 staged 内容，但不自动 `git commit`。
- 用户明确要求“提交”或“创建 commit”后，Agent 才可以执行 commit。
- 默认不执行 `git push`，除非用户明确要求。
- commit 前必须展示或报告待提交文件和 commit message。
- 不得通过 `git add .` 把无关文件、密钥、客户数据和构建产物带入提交。
- 不得重置、覆盖或清理用户已有改动。

## 6. 评审规则

评审优先看：

1. 数据越权、SSRF、凭据泄露和证据篡改。
2. 状态机非法流转、重复事件、丢失告警和错误重试。
3. 检测误报、漏报和不可解释结论。
4. API 契约、迁移兼容性和租户边界。
5. 测试缺口和不可观测的失败路径。

PR 或合并说明至少包含：

```text
目标
改动
风险
测试与结果
数据库/配置/迁移影响
回滚方式
```

## 7. 发布规则

开发提交、合并和发布是三个不同动作：

```text
commit -> review/merge -> release
```

发布必须具备：

- 明确版本或构建标识。
- 数据库迁移顺序和回滚策略。
- 配置和密钥变更清单。
- 关键健康检查。
- 监控和告警确认。
- 失败后的停止和回滚方案。

未经验证的自动恢复、生产网站修改和基础设施变更不得作为普通发布步骤。

## 8. 变更分类

| 分类 | 示例 | 最低要求 |
| --- | --- | --- |
| 文档 | 说明和 ADR | 文档检查 |
| 低风险代码 | 展示、普通查询 | 格式化、编译、相关测试 |
| 领域变更 | 状态机、评分、基线 | 单测、迁移检查、事件回归 |
| 安全变更 | SSRF、权限、凭据、隔离 | 负向测试、审计、人工复核 |
| 高风险操作 | 恢复、删除、外部配置 | 明确授权、演练、回滚验证 |

## 9. 生成物和环境

- `.env`、密钥、证书、客户数据和真实证据不得提交。
- `.idea/` 等个人 IDE 配置默认不属于产品提交。
- 测试夹具应使用合成数据和脱敏页面。
- 生成代码必须注明来源和生成命令，源文件变更后重新生成。
- 本地 MinIO、PostgreSQL 和 Redis 数据目录不得进入 Git。
