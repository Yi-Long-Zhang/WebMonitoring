# ADR-0001：MVP 基线架构

状态：Accepted
日期：2026-09-07

## 背景

产品需要同时检测静态 HTTP 内容和依赖 JavaScript 的页面行为，并保存网页
篡改证据。当前项目处于 MVP 可运行阶段，需求、规则和领域模型仍会快速演进。

## 决策

采用：

- Vue 3 + TypeScript + Vite 管理后台。
- Go 模块化单体作为控制面。
- Go HTTP Worker 执行低成本基础检测。
- Node.js + Playwright Browser Worker 执行浏览器行为检测。
- PostgreSQL 保存业务元数据。
- Redis Streams 传递异步任务和结果。
- S3 兼容对象存储保存原始证据。
- Docker Compose 作为本地和小规模部署基线。

控制面不直接执行不可信网页脚本，浏览器检测独立运行并受网络和资源限制。
当前控制面使用配置的默认租户，资产通过 HTTP 文件完成授权验证后才允许检测。

## 原因

- Vue 适合密集型管理控制台，团队偏好明确。
- Go 适合 API、任务编排和高并发 HTTP 检测。
- Playwright 对渲染、导航、弹窗、下载和资源观察的能力更完整。
- PostgreSQL 适合租户、事件和状态机的事务一致性。
- Redis Streams 提供足够的异步解耦能力，避免过早引入复杂消息平台。
- 对象存储适合截图、HTML 和 HAR 等大文件。

## 未采用的方案

### 全部使用 Go 浏览器驱动

不作为首选。浏览器行为、版本管理和调试生态优先选择 Playwright。

### 一开始拆成完整微服务

不采用。当前领域边界尚未稳定，模块化单体更容易保持事务和快速迭代。

### 只做截图对比

不采用。截图无法解释脚本、表单、跳转、资源和 DOM 结构变化。

### 让大模型直接判定篡改

不采用。检测结果需要可重复、低成本、可审计；AI 只做辅助分析。

## 约束与代价

- 需要维护 Go 和 Node.js 两套 Worker 运行时。
- 浏览器 Worker 必须承担更严格的容器和网络隔离成本。
- Redis Streams 的重试、幂等和死信策略需要自行明确实现。
- 需要继续完善证据保留期和短时签名访问；当前已具备对象摘要校验和下载前完整性校验。

## 退出条件

满足以下条件之一时重新评估架构：

- 控制面发布频率和团队边界使模块化单体成为主要瓶颈。
- 队列吞吐、重试和可观测性需求超过 Redis Streams 的运维能力。
- 多地域检测和数据驻留要求需要区域化控制面。
- 浏览器 Worker 的安全隔离需要独立集群或专用调度平台。

重新评估必须新增 ADR，不能只在代码中替换组件。
